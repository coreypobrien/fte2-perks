# Native chip rules recovered for build 26090957

The output in `data/native/mod-chip-rules.json` is generated by `scripts/extract-native-rules.py`. It reads the installed executable, verifies its exact SHA-256, and checks reflected property names, offsets, enum metadata, and audited constructor stores. It reads no manual in-game observations.

## Defaults and class eligibility

- `Type` is native member offset `0x1f8`. Enum metadata records Core=0 and Modifier=1. Constructor RVA `0x21c130c` writes zero to Type and the adjacent ReplacerType byte.
- `RestrictionType` is member `0x478`. Enum metadata records None=0, Role=1, Kit=2. The constructor does not override this zero-initialized scalar. Epic's [Gameplay Classes documentation](https://dev.epicgames.com/documentation/unreal-engine/gameplay-classes-in-unreal-engine) describes the engine initializing object fields to zero/null before the constructor runs.
- Socket validation at RVA `0x1ec4428` dispatches on RestrictionType: None bypasses the class/role gate; Role compares RoleRestriction; Kit calls the class predicate. A universal restriction does not waive compatibility, ownership, or geometry rules.
- `IsKitAllowed`, exposed through wrapper RVA `0x21c6600`, invokes predicate RVA `0x1eb8620`. It accepts the requested character class when it derives from KitRestriction, or derives from any entry in AlternativeKitsAllowed.
- `OriginKit` is not read by that predicate. A nonempty KitRestriction alongside omitted RestrictionType does not restrict the chip; the None default matters.
- No packaged chip explicitly serializes Role in the inspected dataset. Its role values remain further research scope rather than guessed class mappings.

## Compatibility query

Function RVA `0x1e9d030` requires a Core host and a Modifier candidate. It copies the core's ModifierCompatability container, builds an AnyTagsMatch query through RVA `0x3999530` (expression type1), and matches it against the modifier's effective Tags at RVA `0x39996a0`.

The AnyTagsMatch evaluator at RVA `0x3995dd0` checks queried compatibility tags against both explicit modifier tags and their parent-tag array. Consequently a modifier tag `A.B.C` can match a core compatibility tag `A.B`; the reverse prefix direction is not sufficient. Empty compatibility has no matching Any tag.

The same group-compatibility function has an additional guard: when the incoming modifier has a non-null GrantedAbilityOverride, it rejects a group already containing any chip with a non-null GrantedAbilityOverride. This is a per-group exclusion, not a global one.

## Connectivity and group assignment

`GetPossibleGroupsFromSocketingChip` at RVA `0x1eb1cb0` invokes the perimeter routine at `0x1eb0460`. The latter examines four orthogonal neighboring coordinates around occupied cells of the shape; diagonal-only contact is insufficient.

For each adjacent placed chip, native code resolves its group and the Core in that group, then checks the new modifier against that Core. This permits indirect modifier chains. Every intervening modifier must belong to the same compatible Core group; an incompatible modifier cannot act as a connector.

Each placed chip has one group GUID. If several groups are possible, the code returns distinct group choices. A per-core BFS that accepts a modifier whenever it is reachable from any compatible host is useful pruning, but is not by itself a proof of a legal assignment when a bridge modifier would need to belong to two different groups. For final validation, assign each modifier to one Core group and require an orthogonally connected path entirely within that group; apply the override exclusion to each assignment.

The native socket function creates Core groups separately. Adjacent Core tiles should not automatically merge their ability groups.

## Reproduce and validation

```powershell
python scripts/extract-native-rules.py
```

Use the local Python configured by `scripts/Initialize-NativeTools.ps1` when Python is not on PATH. The recipe pins the executable hash; a patch requires a new audit instead of carrying old addresses forward.

The generated JSON includes disassembly block RVAs and SHA-256 hashes. Enum values are read from reflected metadata rather than assumed. The extractor was run successfully and repeat generation is deterministic. Unknown executables are rejected before PE analysis or output generation.

This is an audited static translation for the known executable. Runtime game behavior has not been directly instrumented. Full acquisition, ownership progression, role values, shape-replacement edge cases, and complex group-merge behavior remain separate research topics.
